=== TASK 12: FARA New/Terminated Registrants ===
Source: DOJ's FARA e-file system (efile.fara.gov), a public Oracle APEX app — NOT a REST/JSON API, but its report pages ARE directly link-accessible with date filters embedded in the URL and no login/session needed (found by hand 2026-09-04, confirmed working cold with no cookies). Two reports, same URL shape, `MM/DD/YYYY` dates, YESTERDAY/TODAY per the usual rolling window:

MOBILE FIRST, WIDER ON DESKTOP — most opens are on a phone held vertically, so the 600px-cap layout below is the base/fallback everywhere, not an afterthought; a separate enhancement then widens it for desktop mail clients that support it. Use the fluid-hybrid technique: the outer wrapper table gets `width="100%"` (HTML attribute) plus `style="width:100%; max-width:600px; margin:0 auto;"` — NOT a fixed `width="640"` — so it actually shrinks to fill a narrow screen instead of getting letterboxed or forcing horizontal scroll/pinch-zoom, and give this table `class="container"` so the desktop rule below can target it. Keep side padding/gutters modest — 16-20px, not 32px+ — so a ~375px-wide phone screen still gets a readable measure of text, not three words per line. Body text minimum 16px (iOS Mail auto-zooms in on anything smaller when the user taps into it, which is jarring); headlines can scale down modestly on narrow screens but stay comfortably larger than body text. Add a `<meta name="viewport" content="width=device-width, initial-scale=1.0">` tag. In the `<style>` block, add `@media (max-width: 480px) { }` rules as progressive enhancement (most modern mail apps honor them; Gmail's app ignores the block but the fluid base layout still degrades gracefully) tightening padding further and bumping body font-size 1-2px if it helps. ALSO add `@media (min-width: 601px) { .container { max-width: 760px !important; } }` in the same `<style>` block (2026-09-04, on request) — this widens the message on desktop mail clients that honor `<style>` media queries (Apple Mail, Outlook.com/desktop, Thunderbird, Gmail webmail in-browser); clients that strip `<style>` blocks (chiefly the Gmail mobile app) simply keep the inline 600px fallback, which is correct there anyway since it's a phone screen. This is a widen-only enhancement layered on the mobile-first base, not a replacement for it — never raise the base inline `max-width:600px`, only this media rule. For the data tables (PTR/PFD trade tables, K Street tables) — these are naturally wide (5+ columns) and WILL be tight on a phone. Do NOT force a CSS `min-width` on them and rely on a `overflow-x:auto` wrapper div to scroll it — that combination is broken in practice: Outlook desktop's Word rendering engine ignores `min-width` entirely and collapses the table to whatever width its container has (columns come out visibly cramped/compressed), while several real mobile mail clients don't reliably contain a scrolling div nested inside a table cell, so the forced min-width blows out the whole message's width instead of just scrolling that one table (2026-08-30: confirmed live — this exact combination produced "compressed on desktop, super wide on mobile" as reported by the reader). Fix: give every data table `width="100%"` with no `min-width` at all, and do NOT set `white-space:nowrap` on any cell — let column text wrap onto 2-3 lines on a narrow screen instead of forcing a fixed column width. This makes the table always fit 100% of whatever container width it's in (mobile or desktop, any client) with no dependency on min-width or overflow-x support. Columns will look tighter on a phone than a wide desktop screen, and that's fine — narrower/wrapped is the acceptable tradeoff, an uncontained horizontal blowout is not. Don't drop table columns to fight this either — full data stays, it just wraps.

This is deliberately LIGHT-ONLY, always — black-on-white/offwhite regardless of the reader's system or email-client dark mode setting. Never add an `@media (prefers-color-scheme: dark)` rule or any dark variant. Lock it explicitly rather than just omitting dark styling: include a real `<html><head>` (this is a standalone email document) with `<meta name="color-scheme" content="light only">` and `<meta name="supported-color-schemes" content="light">`, plus in the `<style>` block: `:root { color-scheme: light only; supported-color-schemes: light; }`, `html, body { background: #f7f5f2 !important; color: #262626 !important; }`, and an Outlook.com dark-mode-lock rule: `[data-ogsc] body, [data-ogsc] table, [data-ogsc] td { background-color: inherit !important; color: inherit !important; }`. Every background/text color anywhere in the document should still be set explicitly inline too (not just relying on the `<style>` block, which some clients strip) — that inline-everywhere approach is itself part of what keeps Gmail's auto-dark-mode from repainting things.
