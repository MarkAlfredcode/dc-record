=== TASK 9: USAspending Contracts ===
Source: `api.usaspending.gov`, no auth needed. Unlike Task 8, this source has real multi-day-to-multi-week posting lag between an award's actual date and when it's visible in the database, and there's no reliable "date this record appeared" field (`last_modified_date` reflects the *award*'s last-touched date, not the specific transaction's — confirmed by hand it resurfaces old already-reported activity whenever anything else changes on the same award; never use it as a novelty filter). So: re-scan a 25-day trailing window every run and diff against `data/usaspending-contracts-manifest.json` (JSON object keyed by each transaction's `internal_id` as a string, value `{"action_date":..., "award_id":..., "recipient":...}`, committed back to the repo the same way as Task 8's manifest).

Steps:
a. WINDOW_START = TODAY minus 25 calendar days.
b. Read `data/usaspending-contracts-manifest.json`.
c. Page through `POST https://api.usaspending.gov/api/v2/search/spending_by_transaction/`, incrementing `"page"` until `page_metadata.hasNext` is false (expect ~60-90 pages, that's normal):
```json
{"filters":{"award_type_codes":["A","B","C","D"],"time_period":[{"start_date":"WINDOW_START","end_date":"TODAY","date_type":"action_date"}],"award_amounts":[{"lower_bound":2000000}]},"fields":["Award ID","Recipient Name","Transaction Amount","Awarding Agency","Awarding Sub Agency","Transaction Description","Action Date","Mod","product_or_service_description","naics_description"],"page":N,"limit":100,"sort":"Transaction Amount","order":"desc"}
```
d. Keep only rows where `"Mod"` is exactly `"0"` (a new base award, not a modification/option-exercise/funding action — those carry a mod number/letter and are out of scope regardless of size). The `award_amounts` filter already limits to $2M+ server-side.
e. For each such row, check its `internal_id` against the manifest. Already present → skip. Not present → new-to-report: add to a working list and add it to the manifest.
f. For every new-to-report award, fetch `GET https://api.usaspending.gov/api/v2/awards/<generated_internal_id>/` (use `generated_internal_id`, not `internal_id`) for the full description. Write 2-4 sentences: who, what agency, plain-English translation of what it's actually for (don't just paste the raw jargon description), the dollar amount, and anything that stands out (sole-source vs. competed if evident, a small/new-looking company winning a huge award, a notable recipient, an unusual description for that agency) — say plainly when nothing stands out rather than manufacturing significance.

MOBILE FIRST, WIDER ON DESKTOP — most opens are on a phone held vertically, so the 600px-cap layout below is the base/fallback everywhere, not an afterthought; a separate enhancement then widens it for desktop mail clients that support it. Use the fluid-hybrid technique: the outer wrapper table gets `width="100%"` (HTML attribute) plus `style="width:100%; max-width:600px; margin:0 auto;"` — NOT a fixed `width="640"` — so it actually shrinks to fill a narrow screen instead of getting letterboxed or forcing horizontal scroll/pinch-zoom, and give this table `class="container"` so the desktop rule below can target it. In the `<style>` block, add `@media (max-width: 480px) { }` rules as progressive enhancement (most modern mail apps honor them; Gmail's app ignores the block but the fluid base layout still degrades gracefully) tightening padding further and bumping body font-size 1-2px if it helps. ALSO add `@media (min-width: 601px) { .container { max-width: 760px !important; } }` in the same `<style>` block (2026-09-04, on request) — this widens the message on desktop mail clients that honor `<style>` media queries (Apple Mail, Outlook.com/desktop, Thunderbird, Gmail webmail in-browser); clients that strip `<style>` blocks (chiefly the Gmail mobile app) simply keep the inline 600px fallback, which is correct there anyway since it's a phone screen. This is a widen-only enhancement layered on the mobile-first base, not a replacement for it — never raise the base inline `max-width:600px`, only this media rule. For the data tables (PTR/PFD trade tables, K Street tables) — these are naturally wide (5+ columns) and WILL be tight on a phone. Do NOT force a CSS `min-width` on them and rely on a `overflow-x:auto` wrapper div to scroll it — that combination is broken in practice: Outlook desktop's Word rendering engine ignores `min-width` entirely and collapses the table to whatever width its container has (columns come out visibly cramped/compressed), while several real mobile mail clients don't reliably contain a scrolling div nested inside a table cell, so the forced min-width blows out the whole message's width instead of just scrolling that one table (2026-08-30: confirmed live — this exact combination produced "compressed on desktop, super wide on mobile" as reported by the reader). This makes the table always fit 100% of whatever container width it's in (mobile or desktop, any client) with no dependency on min-width or overflow-x support. Columns will look tighter on a phone than a wide desktop screen, and that's fine — narrower/wrapped is the acceptable tradeoff, an uncontained horizontal blowout is not. Don't drop table columns to fight this either — full data stays, it just wraps.
